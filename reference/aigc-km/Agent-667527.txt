**文章摘要**

本文是一篇关于构建AI Agent（智能体）的深度反思与技术探讨。作者以腾讯内部一个代码诊断Agent项目的实际经历为切入点，深入剖析了“Harness”（即对Agent的约束、编排与管控系统）在当前技术阶段所面临的困境与边界。文章的核心观点是：**现阶段做好Harness的成本极高，其本质是用有限的、静态的模板去应对无限的、动态的真实问题，这导致投入产出比不佳，且约束本身会随着模型能力的提升而迅速贬值。**

**文章重点总结**

1.  **核心问题：Harness的“双刃剑”效应**
    *   **现象**：一个订单诊断Agent在处理需要“动脑子”的问题时，表现反而不如早期的“乱翻”版本。作者通过对比Cursor和自家Agent的排查路径，发现根源在于：**Harness在托住系统下限的同时，也压住了能力上限**。它通过限制探索来保证稳定性，但真正困难的问题恰恰需要探索。

2.  **Harness的七大管控难题**
    *   文章将Harness拆解为七个必须管理的方面，并逐一指出“做了”和“做好”之间的巨大鸿沟：
        *   **动作空间**：无法动态提供工具，只能写死白名单，导致Agent无法灵活应对新问题。
        *   **上下文构造**：依赖人工注入信息，无法验证知识完备性，一旦遗漏关键信息（如术语表），Agent会“一本正经地犯错”。
        *   **状态传递**：中间结果本质是自然语言，无法结构化，导致信息在传递过程中被误读。
        *   **终止与预算**：只能靠拍脑袋的硬数字（如`maxTurns: 12`），无法根据任务难度动态调整，导致简单任务浪费，复杂任务不够。
        *   **校验门禁**：只能校验形式（如JSON格式），无法校验内容正确性，形成“能验的都不重要，重要的都验不了”的困境。
        *   **失败恢复**：只有“兜底”（给个东西），没有“恢复”（知道错在哪步并回退）。
        *   **可观测**：只能定位到“哪一步”错了，无法定位“为什么”错，归因仍需人工。

3.  **根本矛盾：有限的模板 vs. 无限的问题**
    *   所有Harness规则的困境都源于一个结构性矛盾：**Harness是在提前为问题写好解法模板，而真实的问题空间是无限的，模板是有限的。** 这导致三个具体困境：找不到通用模板、约束与自由度的平衡点无法事先确定、约束条件本身无法标准化。

4.  **业界共性与参照系**
    *   文章指出，这些困境并非个例，而是业界普遍存在的，其根源在于“评估困难”（缺乏廉价的正确性信号），并由此引发长程一致性差、自我评估失效、归因能力缺失等一系列连锁反应。
    *   通过与Claude Code/Cursor等优秀产品的对比，作者发现：**成功的产品将力气花在“给能力”上（如开放探索、廉价反馈、自动上下文管理），而我们的项目将力气花在“加约束”上。**

5.  **反直觉的推论：现阶段做Workflow可能比做Harness更划算**
    *   作者通过对比“纯Workflow”、“重Harness+Agent”和“高自主Agent”三种形态，认为中间档的“重Harness”投入最大、上限被压、下限不稳、维护成本最高，是最不划算的。
    *   **建议**：高频且收敛的问题做成Workflow（稳定、可测试）；长尾且错误成本低的问题给Agent高自主度；中间档的重Harness尽量少做。

6.  **Harness的“半衰期”与未来展望**
    *   **核心观点**：每条Harness规则都是在补偿当前模型的缺陷。模型变强后，这些规则会从“保护”变成“枷锁”，且腐化过程非常安静，让人误以为模型没有进步。
    *   作者认为，真正值得投入的只有那些与模型能力无关的部分：**权限边界、成本控制、可观测性、审计**。
    *   文章最后展望了未来Agent所需的AI原生组件（如记忆层、代码分析组件、流程运行时、上下文管理），认为这些组件成熟后，做好Harness才会变得简单。

**评价**

本文是一篇极具深度和诚意的技术反思文章。它没有停留在技术实现层面，而是深入探讨了AI工程中“控制”与“自由”的哲学矛盾，提出了“Harness有半衰期”、“Workflow可能比Harness更划算”等反直觉但极具启发性的观点。文章逻辑严密，案例生动，从具体问题出发，层层递进到抽象原理，最后给出可操作的工程建议，对从事AI Agent开发的团队具有极高的参考价值。其最大的亮点在于敢于承认“我们做不好”，并冷静分析了“为什么做不好”以及“现在该做什么”，这种务实和自省的态度在技术文章中尤为珍贵。
正文: 好看之后大概三个月，我发现一件挺别扭的事：我们的 Agent 可靠了，但它也变笨了。指标是真好看，可但凡遇到一道稍微需要动点脑子的题，它反而不如三个月前那个满仓乱翻的版本。
一开始我以为是哪儿调坏了。查到后来才慢慢接受另一种可能：不是我们做得不够好，是 Harness 这件事在现阶段做好的成本太高了。

一、从一道答错的题说起
前段时间我在测试订单诊断 Agent，有笔订单报错「系统繁忙」，就直接问它：这笔订单为什么报错系统繁忙。
Agent 跑了一圈，锁定了日志里分数最高的一个并发错误码 268527336，围着它查了几轮，发现对不上，最后输出「材料不足，无法定位」。
同一个问题，我在 Cursor 里原样问了一遍，它答对了。
有意思的是两边用的是同一档模型。差别全在过程里：
Cursor 是这么查的，从用户那句话本身出发：

用户原话
系统繁忙

全仓搜
这句文案

找到默认
转义规则

反查哪些码
落到这句

按时间线
撞到 -202

确认是 RPC
失败未映射

我们的 Agent 是这么查的，从系统算好的候选表出发：

候选错误码
排序表

跟着最高分
268527336

在预选路径
里验证

对不上
用户那句话

结论
材料不足

Cursor 是从「用户能看见的现象」往回倒推，我们的 Agent 是从「系统算出来的高分候选」往下验证。前者的入口是开放的，后者的入口在进模型之前就已经被我们自己洗过一遍了。
那张候选排序表是我们做的，那个「只能在预选路径里读代码」的限制也是我们加的。当初加它们，是因为不加的话 Agent 会满仓乱翻、烧掉大把 token 还找不着北。加了之后确实稳了，代价是它再也学不会 Cursor 这一招。
这件事让我意识到，我们花了几个月建的那套东西，一边在托住下限，一边在压住上限。而且压得比托得更狠。
顺着这个念头往下想，我得到了三个推测：
第一，Harness 的本质是提前给问题写好解法模板，可问题空间是无限的，模板是有限的。这个缺口不会因为我们更努力就收敛。
第二，以现在的模型能力，同样的人力投到 Workflow 上，收益大概率比投到 Harness 上高。
第三，今天写的 Harness，大部分是在补偿模型当下的缺陷。模型变强之后，它们会从保护变成枷锁。所以这类投入应该按半衰期估值，而不是按当下收益。
第三条是我自己最不愿意承认的一条，因为它意味着我们过去半年干的活儿，有相当一部分是在给一个正在自愈的伤口反复换药。

二、我理解的「Agent」和「Harness」
Agent 把 LLM 当决策器，放进一个「感知—决策—行动—反馈」的闭环里，并且给了它对外部世界真实的操作权。可以最终输出证据闭环的才能算Agent。
关键不在于模型多强，在于谁在决定下一步做什么。下一步是程序写死的，那是工作流；下一步是模型看完上一步的结果自己挑的，才有 Agent 的成分。
所以有些AI工具不算Agent，也不在这次讨论范围内：
有没有行动能力。纯 LLM 是个函数，文本进文本出，没有副作用。Agent 得能改变外部状态或者获取外部信息——读文件、发请求、写库。只会输出文字建议的，包装得再漂亮也还是个 LLM 应用。
有没有规划能力。单次「prompt 进、回答出」不是 Agent，哪怕这个 prompt 有五千行。Agent 的本质是输出动作、拿到观察、基于新观察再决定下一个动作，一直转到它认为该停了。没有 loop，就没有 Agent。
控制权在谁手上。终止条件谁定的？路径谁选的？模型自己判断「够了，可以下结论了」，那是 Agent；代码规定「跑完这四步就结束」，那这一层是编排。
有两个说法我觉得站不住。
「在 LLM 上做了应用就算 Agent」——RAG 问答、翻译网页、prompt 模板平台，都没有闭环也没有行动权，不算。

「封装够深、定制够重就算 Agent」——你可以把 LLM 封装得极重，做出一个特别复杂的文案生成系统，它依然不是，因为每次都是单向的一次性推理。封装深度是工程量，自主闭环是架构，这两件事是正交的。

我们那个代码分析项目正好是个不错的样本：整体是编排系统，但每个 Phase 内部是真 Agent。Phase 之间的数据靠 JS 变量搬、顺序由代码定死，这一层不是 Agent 行为；Phase 2 里每个搜索任务自己决定搜什么词、读哪个文件、什么时候算搜够了，这一层是。
所以「是不是 Agent」像是一个需要精确控制的旋钮。往上拧，能力上限高，方差也大；往下拧，稳，但天花板也跟着下来了。
Harness 就是这个旋钮的实现方式。而我们做不好它，说到底是因为不知道该拧到几度，也没有任何工具能帮我们量。
我们前一篇里吐槽的那些毛病，爱见好就收、手痒调 Bash、跟自己较劲评三次分，全都是控制层面的失控，不是生成质量问题。也确实光靠调 prompt 治不好。

三、Harness 我可能没有一件现在能管的很好
Harness 这个词被用得太轻了，好像就是加点约束、做点编排。真拆开看，它至少要管七件事。

Agent 运行时

感知

决策

行动

反馈

① 动作空间管理
给哪些工具

② 上下文构造
喂哪些信息

③ 状态传递
阶段间交接什么

④ 终止与预算
什么时候停

⑤ 校验门禁
这步对不对

⑥ 失败恢复
走偏了怎么退

⑦ 可观测归因
错在哪一步

这七件我们全都「做了」。往下看会发现，做了和做好之间隔着的东西挺一致。

3.1 动作空间：该给哪些工具，没人知道
最理想的形态是动态的，每个情境给恰好够用的工具。工具太多模型选择困难，太少又干不了活。
我们的实现是一行写死的白名单，搜索阶段就 Read / Glob / Grep 三个。
为什么不做成动态的？因为一想就撞墙：要判断「这个任务需要哪些工具」，得先理解这个任务，而理解任务恰好是模型的活儿。你没法在调模型之前就知道该给模型什么。于是只能退回按阶段粗粒度切一刀，代价开头已经见过了——订单诊断的代码验证只能在预选路径里读，它这辈子都不会想到先去全仓搜一句错误文案。

3.2 上下文构造：缺了什么，缺的时候没人知道
每一步该喂什么信息，我们是手工分的层：一个精简的角色定义、每阶段一份 prompt 模板、几份按需注入的参考资料，哪个阶段注入哪一份，人拍的。
这套东西平时跑得挺好，直到有一天你发现术语表里少了一行「union 在我们代码里是合单不是联合」。少这一行，Agent 必错，而且是那种一本正经的错。
麻烦的不是缺，是没有任何机制能提前告诉你缺了。知识的完备性无法验证，你只能等它错一次、补一行，然后等下一次。

3.3 状态传递：中间结果是一段自然语言
阶段之间怎么交接？我们的做法是把上一阶段的搜索结果拼成字符串，塞进下一个 prompt。
信息是不会丢了——搬运工是代码不是模型的记忆，这一点比之前强太多。但信息会被误读。上游写的是「该功能已定义但未找到调用入口」，下游读成「该功能存在」，中间没有任何一道闸门能拦住。
根子在于中间状态本质上是一段自然语言：定不了 schema，做不了 diff，也没法增量更新。你在两个模块之间传的不是数据，是一段需要重新理解的话。

3.4 终止与预算：这个数字是怎么来的
我们的终止条件是 maxTurns: 12 加十五分钟全局超时。这个是怎么定的？试出来的，没有别的道理。
想定得有道理也不行——「证据是否充分」需要领域判断，能做这个判断的只有模型，而模型的自我评估系统性偏乐观。于是只剩下和任务难度完全无关的硬数字，三轮对简单问题是浪费，对难题远远不够。
后来我们上了 TAO 多轮调查环，让模型每轮结束后自己想想证据够不够、下一步往哪查。这一版给我的打击比较大：轮次从三加到五、加到十，答对率基本没动。入口选错的时候，多给几轮只是让它在错误的假设上多转几圈。

3.5 校验门禁：能验的都不重要
我们能验的只有形式——JSON 能不能 parse、字段在不在、mermaid 语法合不合法。
这里有个挺讽刺的规律：能被代码验证的东西，恰好是最不重要的东西。解析函数能保证拿到一个合法的搜索任务数组，但保证不了这三个目录是对的。前者从来不出事，后者天天出事。
说到底是因为代码诊断这个领域没有「编译通过」「测试变绿」这种一分钱不花就能拿到的对错信号。这是它和编程 Agent 最大的差距，第十节还会再算这笔账。

3.6 失败恢复：兜底不是回退
走偏了怎么办？我们的答案是一组预定义的默认搜索路径，规划失败就用它凑合。
这是兜底，不是恢复。兜底的意思是「我不知道哪儿错了，但我保证给你个东西」；恢复的意思是「我知道第几步错了，退回去换条路」。后者我们完全做不到。
因为回退需要中间过程的对错标签，而我们手上只有最终结果。Agent 顺着高分错误码往下查五轮，每一步单独看都挑不出毛病，错的是第一步选的入口——偏偏那一步在当时看起来最合理。

3.7 可观测：知道错在哪一步，不知道为什么
七件事里这件我们做得最好。每个阶段的动作、评分、结果长度、耗时全都入库，一条 SQL 拉出完整轨迹。
但也就到这儿了。知道规划阶段选错了目录，不知道它为什么选错——术语表缺失？问题理解偏了？还是这次模型就是抽风了？能定位到「哪一步」，定位不到「为什么」，归因还得靠人一个 case 一个 case 看。

四、核心的那道坎：有限的模板，无限的问题
把上面七件事排一排，会浮现出一条挺清晰的分界线。
能做好的，全是那些不管用户问什么都一样的部分；做不好的，全是必须随问题变化的部分。
说到底，Harness 是在提前给问题写好解法模板，而问题空间是无限的，模板是有限的。
这句话听着抽象，拆成三个具体的困境就好懂了，而且每个都能在我们项目里找到对应的伤疤。
一是找不到通用的解法模板。每写一条 Harness 规则，其实都是在断言「这类问题应该这么解」。但「这类」的边界永远画不准。我们为了修一个「合单支付搜错目录」的 case，在规划阶段加了一条强调「合单」和「联合」区别的规则。结果呢？所有跟这两个词八竿子打不着的问题也跟着受影响，Agent 开始在每次规划的时候都要纠结一下「这个是不是跟合单有关」。规则的作用域，没办法精确限定在它本该管的那些问题上。
二是约束和自由度的平衡点根本没法事先定。同一个 maxTurns: 12，对「查一下这笔订单金额」是浪费，对「这笔订单为什么报错系统繁忙」是远远不够。同一句「只在预选路径里读代码」，对已知模块的问题是加速，对需要全仓反查一句文案的问题是致命的。平衡点不是一个值，它是问题的函数——可我们只能配一个常数。
三是约束条件本身没法标准化。「证据充分」在订单诊断里是什么？在代码分析里又是什么？没有一个跨问题通用的定义。所以我们只能往两个极端退：要么是跟内容完全无关的硬预算，要么是为单个 case 手写的特例判断。前者太粗，后者不泛化，中间那一大片「该有个标准但给不出标准」的地带是空的。
所以做不好 Harness，真不是工程能力的问题。是我们在拿一个有限、静态、需要人提前穷举的东西——代码规则，去覆盖一个无限、动态、每次都不一样的东西——真实问题。

图片引用: https://km.woa.com/asset/00010002260800783e51b5f4464aad01?height=848&width=1264

这两者之间的差是结构性的。你可以把它从很大缩到比较大，但缩不到零，而且越往后每缩一点付出的代价越高。我们过去半年就一直在这个边际收益递减的区间里加班。

4.1 更难受的是：Harness 越强，Agent 越笨
顺着上面的逻辑再走一步，会发现一个更让人泄气的现象。
我们收紧动作空间，Agent 就不会先去全仓搜「系统繁忙」这句文案了。我们做候选排序帮它聚焦，它就被高分错误码带着走了。我们固化调查流程，换一类问题它就走不通了，只能不断加特例分支。
Harness 是用「限制探索」换「保证下限」。而真正难的问题，恰恰需要探索。
这里先埋个伏笔：如果 Harness 的主要作用是补偿模型的缺陷，那它就有两个直接推论。一是模型变强之后，这些补偿会失效，甚至反过来变成阻碍。二是既然目的只是保下限，那用更简单、更稳、更好维护的 Workflow 来保，可能是笔更划算的买卖。这两点我放到后面专门讲。

五、这些坑不是我们独有的
上面讲的都是自己项目里的事，容易让人觉得是我们水平不行。所以有必要跳出来看一眼：业界现在卡住的地方高度一致，而且这些坑之间是有因果的，不是一张并列的清单。

我把「评估困难」放在最前面，因为它是所有问题的元问题：没有评估就没有迭代，只有手感。下面这几条，多多少少都是它的下游。
最先撞上的通常是长程一致性。任务链一长，前面的约束和结论就开始漂。我们最典型的一次是 Agent 搜了验密模块十二个文件，最后的回答只基于最后三个，把「签名验证」和「密码验证」混着说了——领域知识那部分早被挤出去了。指望窗口变大来解决是不现实的，注意力就那么多，压缩和摘要又都是有损的，而你不知道丢掉的是不是关键那条。
比这更根本的是它判断不了自己做够没有。搜完第一个模块就觉得差不多了，输出一份结构完整、流程图漂亮、但压根没碰到合单核心逻辑层的回答。这不是 bug，是训练目标决定的倾向：模型被训练成生成看起来对的内容，不是承认不知道。所以那些 confidence: 0.65 之类的置信度基本是编的，跟真实正确率对不上——这也让「用置信度做门禁」这条路走不通。
归因是另一个硬伤。日志里同时躺着并发错误码、Get 空、RPC -202，Agent 挑了分数最高的那个当主因，真正的主因是 -202 经默认转义变成了「系统繁忙」。因果判断需要反事实推理——「如果没有这个错误，还会失败吗」——而 Agent 只能看到一次已经发生的执行轨迹，它没有做实验的能力，就只能拿相关性凑合。
前面几条叠在一起，就长出了探索策略贫乏：不会主动换角度，一条错路能走到黑。TAO 加轮次没用就是这个道理，它缺的不是轮次，是「我这个假设可能整个是错的」这种念头。人类开发排障是日志和代码来回交叉核对，走不通会整个换个假设重来，Agent 不会。
还有一条特别隐蔽的：它不知道自己缺什么知识。Skill 里没写「系统繁忙等于未映射错误的默认转义」，Agent 就不会主动去代码库里发现这条规则——它甚至不知道有这么一条规则需要去查。于是知识库成了无底洞，每个 case 补一条，永远补不完，补多了还互相打架。
最后是很现实的一条：成本和延迟。多轮加多阶段再加 verifier，账涨得很快。我们调试一个问题反复跑，每次三五万 token；有段时间百分之八的请求会撞上十五分钟超时，拆开看搜索阶段占了七成以上。这等于把「多想几轮」这个最简单的提质手段直接掐死了——很多时候不是不能想得更久，是想不起。

六、拿 Claude Code 当参照系，看看差在哪
回到开头那道题：同样的模型，Cursor 答对了我们答错了，它到底多了些什么？
分析claude code的模式拆下来大概是三组能力。
第一组是探索层面的，也是决定那道题胜负的。它的入口是开放的，而且是从现象出发——先搜用户原话，再顺着找转义规则，而不是从一份系统算好的高分候选表往下验证。配合这个入口的是「动作足够廉价」：绝大多数操作是只读的，搜错了没有任何副作用；写操作有 diff 能回滚；跑个测试立刻有红绿信号。错误便宜，才敢让它自己乱走，这条后面会展开成一条原则。
第二组是上下文层面的。读哪个文件、读多少行、什么时候该丢，它自己决定，窗口逼近时还能自动压缩。复杂任务它会开子任务，每个子任务有独立窗口，主流程只拿一份摘要回来。这里最值得学的一点是：上下文隔离比上下文扩容更有效——我们那个四阶段架构无意中做对的也是这件事，只不过是手工版的。相比之下我们的上下文是人工分层、静态注入，想调整得改代码。
第三组是工程层面的，看着朴素但差距最大。工具是产品级的，参数 schema、错误返回、权限确认都正经设计过，不是在 prompt 里描述两句；记忆是分层的，全局、项目、会话各管一摊，而我们只有「最近三轮问答」这种原始做法；最关键的是人可以随时插手——打断、改方向、拒绝某个操作。允许人接管做不好的那部分，比假装能自动做好有用得多。
摆在一起看：

Claude Code / Cursor我们的 Agent
探索全仓自由检索白名单路径
反馈信号编译、测试、diff基本没有
上下文自动压缩 + 子任务隔离手工分层静态注入
工具一等公民够用就行
记忆全局 项目 会话分层最近三轮
人在环随时介入一问一答

这张表其实就是全文答案的一半：我们把力气全花在了「约束」上，人家把力气花在了「给能力」上。

七、自由度和 Workflow 的平衡点在哪
「自主决策做不好，硬约束又管太死」这个张力是真实存在的。但我觉得它之所以看起来无解，是因为大家把自主度当成了一个旋钮。做得好的系统其实是把它拆成了好几个旋钮，分别拧到不同位置。

图片引用: https://km.woa.com/asset/000100022608005e0fca9f0696419f01?height=848&width=1264

7.1 约束动作空间，别约束动作选择
这条最关键。「Agent 老爱用 Bash」的正确解法，不是在 prompt 里禁止——那是软约束，大概七成有效——也不是把流程写死，而是让 Bash 这个动作在物理上不存在。
推广开来就是：代码负责定义菜单，模型负责点菜。菜单可以很小，只有三个工具，但点哪个、点几次、什么顺序，完全由模型自己定。这样既拿到了确定性，又保住了灵活性。
关键区别在于你限制的是能力边界还是执行路径。真正伤害泛化的是后者。
回头看我们自己，那个「只许在预选路径里读代码」的限制，已经越过界了——它限制的是路径不是边界。所以订单诊断 Agent 永远学不会 Cursor 那一招，这不怪模型。

7.2 在错误便宜的地方放手，在错误昂贵的地方收紧
自主决策之所以让人害怕，是因为错了代价大。那另一条路就是降低单次错误的成本，而不是降低犯错的概率。
只读工具比写工具安全得多，搜错了也没有副作用；schema 校验让失败立刻可见，而不是带着脏数据往下走；有降级路径，解析失败就用预定义方案，答案差一点但不至于卡死。
这三条我们其实都做到了。所以按这个原则倒推，我们的搜索阶段本来是可以更放开的——只读、有轮次兜底、错了几乎零代价，完全可以允许它在发现结果不足时自主追加一轮。反倒是最终输出的格式，得继续用代码硬校验，因为那是用户直接看到的，错了代价大。
「在错误便宜的地方给自主权，在错误昂贵的地方给约束」——这比笼统地问「该给多少自主度」更能指导具体决策。

7.3 让模型出计划，让代码去执行
这条是前两条的一个具体用法：规划本身是一次模型调用，但它产出的是结构化数据，真正执行的是代码。
我们的规划阶段输出一个任务数组，代码拿到之后再去并行调度。模型有充分的自主权决定搜什么、搜几个、按什么关键词搜，但它没有执行权——它写的是一张单子，不是一条命令。
这个分离带来的好处是计划变得可审计了：代码可以校验字段是否齐全、可以把五个任务裁到三个、解析失败可以整个降级。如果让模型边想边执行，这些卡点一个都插不进去。
顺带说，这也是为什么我不太喜欢那种「一个 Agent 从头干到尾」的架构。不是因为它不聪明，是因为它中间没有任何地方能让你插手。

7.4 平衡点是试出来的，而且要允许往回退
没人能一次就设计出正确的约束边界。可行的做法是个棘轮：先给较高自主度跑起来，收集失败模式，只针对反复出现的失败做固化，而且优先固化那些确定性的、每次都一样的部分，最后才动需要判断的部分。
反向信号同样重要：如果某条硬约束你经常需要手动开口子，说明它固化早了，该退回去交给模型判断。「约束太多」的典型症状就是遇到稍微变形的问题就走不通，只能不断加特例分支。这时候正确的动作是往回退一格。

八、一个反直觉的推论：现在做 Workflow，可能比做 Harness 划算
顺着前面的论证往下推，会得到一个让人不太舒服的结论：既然中间状态做不好，不如干脆退到两端。

纯 Workflow 投入低、上限低但确定、下限高且稳，维护起来就是普通代码。高自主 Agent 投入也不高，上限高但方差大，改 prompt 和工具就能迭代。
中间这一档最尴尬：投入最大，上限被自己的约束压住，下限又没有 Workflow 那么稳，维护成本还是三者里最高的——因为规则之间会互相干扰。
让我改变看法的，主要是这么几件事。
先是发现真正高频的那部分问题本来就是收敛的。我们把最近七天的问题拉出来分了一次类，大头就那么几种：这笔订单为什么失败、扣费顺序为什么不对、这个订单现在什么状态。这几类的排查路径高度稳定，完全可以写死。写死之后正确率比让 Agent 自由发挥高得多，而且能解释、能测试、能回归。
然后是意识到失败的形态不一样。Workflow 走不通就是走不通，会明确报错；Agent 走不通会给你一个自信满满但错的归因。这两种失败的代价差得很远——用户被误导一次，对这个工具的信任就没了。这个账我们真算过，答不出来比答错便宜太多。
还有一点是投入能不能沉淀。一条查询逻辑写好了就一直在那儿，跟模型版本没关系；而一条 Harness 规则的价值，高度依赖当前模型的当前脾气。
最后是分工问题。Workflow 把 LLM 用在了它最擅长的地方——单点的语义抽取、归纳、改写、生成，这些现在的模型做得很稳。而不是把多步规划、自我评估、判断何时该停这几件它最不擅长的活儿一股脑塞给它。

九、Harness 有半衰期，你今天写的约束明天多半要删
比「做不好」更值得警惕的一件事：Harness 大概是所有 AI 工程产物里最容易腐化的一类。
腐化的根源只有一句话——每条约束都是在补偿某个模型缺陷。缺陷被下一代模型修好了，这条约束就从保护变成枷锁。我们写「关键约束重复三遍」，是因为当时模型会漏看长 prompt 里的指令；长上下文注意力改善之后，这三遍就纯粹是在浪费 token、稀释注意力了。
真正麻烦的是它腐化得很安静。当初是为了防止旧模型自己跟自己较劲，新模型可能本来能靠十轮推理啃下更难的题，但这个上限让你永远看不到它变强了。腐化的 Harness 不会报错，它只会让你以为模型没进步。
而且约束之间会长出隐性依赖，想拆都不好拆。候选排序当初是为了帮模型聚焦，后来的调查动作、停止条件全都建立在「有一张排好序的候选表」这个假设上，现在想把排序去掉，得动一整片。
再加上模型的脾气本身也会变——换个版本，原来七成有效的 prompt 约束可能掉到四成，也可能变成过度约束。而我们连一套能发现这件事的回归测试都没有。
我拿前一篇里写的那七步改造逐条问了一遍「如果模型再强一代，这条还需要吗」。诚实地讲，大部分是补丁不是架构。真正会留下来的只有那些跟模型能力无关的部分：权限边界、成本控制、可观测性、审计。
说到底，Harness 的投入应该按半衰期来估值。一条预计半年后就要删的规则，值不值得花两周去调？很多时候答案是不值得。那两周拿去把这类问题做成一个稳定的 Workflow，或者干脆拿去等模型变强，收益都更高。

十、感知、决策、行动、反馈、停止，为什么每一环都难
「Harness 该管什么、我们管到了哪一步」，是从工程侧看。这一节换个视角，从模型侧看：同样这个闭环，为什么它自己转不起来。
结论先画在图上：

信号缺失，环断在这里

感知

行动

五环里，感知、决策、行动都能靠工程手段缓解到勉强能用，唯独反馈这一环缺的是客观信号，而这不是工程能解决的。

10.1 感知：不知道自己没看到什么
感知这一环的困境很朴素：世界是无限的，窗口是有限的，所以感知永远是采样。而采样策略本身就需要智能，这就又绕回去了。
我们踩的坑是 Agent 每次新会话都要重新认路，花两三千 token 搞清楚目录映射和 BUILD target 的对应关系，而且经常记混。
缓解的办法其实有个挺好用的判据：这个信息是不是每次都一样？是的话就是代码的活儿。代码库结构、术语映射、模块架构这些确定性事实，应该由代码查好、结构化好直接递过去，别让模型现场去发现。模型只应该感知「这次任务特有的、需要判断的」那部分。
但没解决的部分更麻烦：它不知道自己没感知到什么。缺一条术语映射，Agent 不会说「我缺信息」，它会非常自信地答错。

10.2 决策：贪心，而且容易被呈现方式带跑
模型选下一步的时候，依据的其实不是逻辑上哪件事更重要，而是信息在上下文里的呈现顺序和显著性。高分候选排在前面，它就跟着走了——那道答错的题就是这么错的。
更要命的是它没有真正的搜索和回溯，是贪心的，选了一条路就一路走到黑。而决策质量在当时又没法评估，只能事后看结果。
我们的缓解是外层确定性、内层自主：阶段序列由代码定死，因为这是我们已知的领域知识；阶段内部的动作交给模型。
代价是外层序列一旦固化，就失去了「换个思路」的能力。开头那道题 Cursor 能做对我们做不对，根子就在这儿。

10.3 行动：非法的拦得住，愚蠢的拦不住
行动这一环，工程手段其实挺管用的：白名单加目录限制加参数校验，能让非法动作在物理上不可能发生。
问题是合法但愚蠢的动作拦不住。Agent 在一个大目录里反复 Grep 同一个关键词的各种变体，十几轮下来把时间全耗光了——每一次 Grep 单独看都完全合规。
粒度也是个没解的问题。一次 Grep 太小，一次「分析整个模块」又太大，中间那个刚刚好的粒度很难设计。再加上动作之间没有事务性，做了一半失败了没法回滚。

10.4 反馈：整个闭环就断在这里
这一环理想上是从环境返回的信息里正确更新认知，但它有三个叠加的问题。
信号质量差。工具返回「未找到」，这到底是「不存在」还是「搜错地方了」？Agent 分不清，说实话我们也分不清。
很多时候压根没有信号。代码诊断这个领域没有编译器、没有测试，没有廉价的对错裁判。这是它和编程 Agent 最本质的差距——编程 Agent 之所以领先，很大程度上是因为它白拿了两个免费的裁判。
反馈还不对称。成功的反馈很弱，搜到一堆代码，然后呢？失败的反馈也很弱，没搜到，不知道为什么。
缓解手段里最靠谱的是「凡是能用代码判定的绝不问模型」，其次是独立的 verifier——另开一次 LLM 调用，只给它检查任务，不给它生成任务。生成和验证的不对称性是关键：判断「这个回答有没有覆盖合单核心模块」，比「写出覆盖合单的回答」容易得多，而且换个 agent 来判会客观不少，同一个 agent 自查约等于没查。
但 verifier 自己也是 LLM，也会错，成本还翻倍。我们设计好的 Review 阶段一直没接进去，就是因为这笔账算不清。

10.5 停止：最不该交给模型的一环
模型的自我评估几乎必然偏乐观，「见好就收」不是 bug 是固有倾向。所以生产系统里的终止条件应该来自三类，都不依赖模型的自我感觉：硬预算（超时、轮次、token 上限，这是保命的，不讲道理）、外部可验证信号（编译过了、schema 通过了、必需字段都填了）、独立的检查者。
这里有个具体做法值得单独说：把「完整性」从模型的主观判断变成代码可验证的客观状态。规划阶段代码就记下必须覆盖的模块清单，汇总之前代码检查清单是不是都有对应的搜索结果，缺了就打回去重搜。这比在 prompt 里写「请务必搜全」有效太多了。
当然，清单本身怎么来？还是靠人预设。绕了一圈又回到那个有限模板的问题上。
把五环连起来看就明白了：反馈断了，停止就只能靠拍脑袋的硬预算；停止不准，决策就没法改进；决策不改进，探索策略永远贫乏。整个闭环是被「没有裁判」这一件事卡死的。

十一、未来的 Agent 需要什么样的组件
暂时不行是成本太高，未来有低成本的「AI组件」后说不定和Workflow一样简单。
上面这些能力不该每个团队自己用胶水代码拼一遍，就像当年做 Web 不需要每个人自己写 HTTP 解析。
「我们到底缺什么」，发现业界这两年恰好就在这四条线上各自长东西。它们有个共同点：这些组件本身也需要 AI 能力，不是纯代码。这正是我们过去几个月做不好的原因——一直在用纯代码实现需要语义理解的东西。

11.1 AI原生组件的期待
记忆层，目前是整个技术栈里最不标准化的一块。三个主流方案对「记忆是什么」的答案完全不同：Mem0 当它是抽取管道，从对话里自动抽事实存进向量库；Zep 当它是时序知识图，每条事实带有效期，过期不是删除而是标记从某时刻起失效；Letta（原 MemGPT）干脆当它是运行时本身，核心、召回、归档分层，Agent 用工具调用编辑自己的记忆。
第三条路线的「自己编辑自己的记忆」则正好治「Skill 无底洞」：新事实由 Agent 写入、按需召回，而不是人工补规则、补到互相打架。至于这层的成熟度——公开评测里不同方案的召回准确率能差二十多个百分点，几家基准还互相对不上，连「怎么算记得好」都没共识。
代码分析组件：用 Tree-sitter 把源码解析成 AST，抽出调用边和依赖关系建成持久化的图，再通过 MCP 暴露给 Agent，让它直接问「谁调用了这个函数」「从 A 到 B 的路径是什么」「改这里影响多大」。「那个错误码从哪儿产生、经过哪些转义、最后变成那句系统繁忙」——本来就该是一次图查询，而不是十轮 Grep。

图片引用: https://km.woa.com/asset/000100022608006a0fbc92fd8c41d201?height=848&width=1264

但有个实验结果值得警惕：有论文把图谱方案和「让 Agent 自由读文件」做对比，图谱方案 token 只用十分之一、工具调用少一半多，答案质量却是 83% 对 92%，反而低了九个百分点。这和本文反复讲的是同一件事——任何以提效为目的的结构化，都会带走一部分探索能力。所以正确形态是几条路并存（精确串用 ripgrep、结构用 AST、概念才走向量），而不是用图谱取代自由探索。我们当年错就错在，不是给 Agent 加了一条更快的路，是把其他路都堵了。
流程运行时，关键在一个区分：checkpoint 保住的是数据，不是执行。你把每步状态都存了盘，但进程一死这次运行还是死了——得有东西去发现它挂了、决定从哪重进、再把它拉起来。这份责任框架不担就得你自己写。对照我们：事件记录很完整，但那只是数据，真出问题没有任何机制能自动重入，只能人看日志手动重跑。第三节说的「有兜底没有回退」，根子就在这儿。
与之配套的是可持久的人工介入：流程停在某一步等人确认，等待不占进程不烧算力，隔一个月回来也能从那一点精确恢复。而我们的做法是十五分钟超时直接掐断——不是不想让人介入，是我们的流程停不起。
上下文管理，套路已经很清楚：接近窗口上限时压缩历史成摘要重开窗口；把可以重新获取的工具返回值替换成占位符、只留调用记录；噪声大的深活扔进子任务的独立窗口，回来只给一两千 token 摘要；大块产物写到外部存储，上下文只留路径。一句话概括——能恢复的先卸载，实在不行才做有损摘要。
对照下来最清楚的是我们那个「关键约束重复三遍」：那不是方案，是没有工具的年代不得不用的土办法。

十二、所以我们到底做不好什么
回到标题那个问题。Harness是正确的，但是要做好成本还是非常高，目前资源有限的场景下，我们能做什么？
能改的是覆盖问题。有限的模板对无限的问题，我们只能一个 case 一个补丁，补丁还互相干扰。这层能改进，但改不彻底。
改不了的是信号问题。代码诊断这类领域没有编译器和测试这种免费裁判，闭环断在反馈这一环，加班解决不了。要么造出裁判，要么就承认这类任务现在只能辅助人，替代不了人。
不该现在改的是估值问题。Harness 有半衰期，它补偿的是模型今天的缺陷。每一笔投入都该先问「这条规则能活多久」，答案常常短到不值得动手。而这四类基础组件成熟之前，「做好 Harness」对绝大多数团队本来就是个伪命题——就像在没有数据库的年代要求每个人做好事务。

图片引用: https://km.woa.com/asset/000100022608006528babbf10940b301?height=848&width=1264

所以：高频且收敛的问题做成 Workflow，长尾发散且错误便宜的问题给 Agent 高自主度，中间那一档重 Harness 尽量少做。我们过去半年恰恰把大部分人力压在了最不划算的中间档。
很多Harness现在确实能用了，但它能用是因为我们把问题域切小了、自主度压低了、兜底做厚了，不是因为它变聪明了。Harness 现阶段的真实定位，是用工程手段兑现模型能力的下限，而不是逼近上限。
如果哪天模型的自我评估变准了、反馈信号变廉价了，我们今天写的这些 Harness 有多少会被直接删掉？
我猜大部分会。而这恰恰说明它们是补丁，不是架构。真正值得现在就投入的，只有那些删不掉的部分——权限边界、成本控制、可观测性、审计。这些和模型多聪明无关。
