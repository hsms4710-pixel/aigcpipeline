AI摘要: **文章摘要**

本文是 MiniMax 开发者关系负责人李元在腾讯 IEG 的分享，主题围绕其最新大语言模型 **MiniMax M3** 的能力，以及如何利用 AI Agent 在个人和组织层面实现全面提效。文章从模型能力展示切入，逐步深入到具体的提效方法论和组织架构变革思考，为读者提供了从工具到管理的完整视角。

**文章重点总结**

1.  **MiniMax M3 的核心能力与游戏开发应用**
    *   **模型优势**：M3 是开源模型中的 SOTA（最先进水平），拥有 **400B 参数**、**1M 上下文** 和 **原生多模态** 能力，在 Coding 和 Agent 任务上表现接近顶尖闭源模型。
    *   **游戏开发场景**：
        *   **原型加速**：M3 大幅增强了对 Three.js/3D 的理解，开发者仅需一个 Prompt 即可生成可交互的 3D 小屋、复刻电影片段等原型，极大加速游戏前期研发。
        *   **专业引擎支持**：M3 初步加强了对 Unity、UE、Godot 等专业游戏引擎的支持，可帮助专业开发者快速搭建小游戏场景。
        *   **AI in Game**：M3 具备强大的 **角色扮演（Roleplay）** 能力，包括世界一致性（不崩设定）、长程稳定性（百轮对话不重复）和偏好感知（懂潜台词），可用于游戏中的 NPC 对话、AI 队友等场景。

2.  **面向个人的 AI 提效方法论**
    *   **核心思路**：将自己视为管理者，将 AI Agent 视为基层员工，通过“发现冗余 → 方案设计 → 流程固化 → 组织复用”的闭环来提效。
    *   **方案设计四步法**：
        1.  **明确交付标准**：任务输出必须可验收。
        2.  **配齐基础设施**：优先推荐使用 **CLI** 而非 MCP 来封装工具，因为 CLI 更节省上下文、支持串行执行和热插拔。
        3.  **完善上下文**：像带实习生一样，为 AI 提供完整的业务背景和规则。
        4.  **积木式迭代**：将复杂任务拆解，逐步搭建并验证。
    *   **流程固化**：通过设置定时任务或 Loop 循环，将已验证的流程自动化，减少人工干预。
    *   **组织复用**：**在群聊中使用 AI Agent**，将操作轨迹和对话沉淀为团队知识库，实现能力传递。
    *   **实战案例（Octopus）**：作者设计了一个名为“Octopus”的 AI Agent，用于自动维护 GitHub 上数千个开源框架的 API 适配。该 Agent 通过主从架构并行工作，上线 3 个月提交了 2700+ 次 PR，成功合入 800+ 项目，将作者从繁琐的重复劳动中解放出来。

3.  **面向组织的 AI 提效与架构变革**
    *   **核心洞察**：单纯给每个人配发 AI 工具，并不能显著提升组织效率。真正的变革需要像福特流水线一样，**重新设计系统本身**。
    *   **组织架构演进**：
        *   **1.0 专业分工**：产品→设计→前端→后端→测试→发布，串行接力，信息损耗大。
        *   **2.0 全栈化协作**：打破职能墙，开放所有代码权限，鼓励“有想法的人”直接用 AI 实现原型，实现基于原型的驱动。
        *   **3.0 目标闭环**：研发线转型全栈，将“交付”与“守护”分离。特性小队（人+AI）负责端到端交付，架构师和测试负责系统质量守护。
    *   **新的人才需求**：未来的工程师需要是 **“T 型人才”**——横向上精通 AI 应用，纵向上在某个领域有极深的专业判断力（如架构师），并能通过 AI 触达相邻工程和非工程领域。

**评价**

本文内容详实、逻辑清晰，既有前沿模型的技术展示，又有极具实操性的个人和组织提效方法论。作者通过生动的案例（如 Octopus Agent）和经典的管理学类比（福特流水线），将复杂的 AI 应用和组织变革讲得通俗易懂。文章不仅提供了工具层面的“术”，更引发了关于组织架构和人才价值的“道”的思考，对希望将 AI 深度融入工作的读者具有很高的参考价值。

其实早在七八年前，我就在 QQ 音乐做推荐算法，当时办公地点就在腾大旁边——那时候 QQ 音乐还没有从腾讯分拆出去，所以也算是前腾讯的员工吧。后来我加入了字节跳动，同样做推荐算法。2023 年我加入了 MiniMax，主要负责文本算法的迭代，也就是现在大家常说的大模型。

大概从去年开始，我们看到 Agent 是一个非常好的产品形态。国内首款这类产品应该是 Manus，它上线大概两三周时，我们内部的研发也刚好推进到这个时间点。那时候是公司内部三五个同学一起搓出了我们的第一款 Agent，我也深度参与，让这款 Agent 产品成功上线。之后我就不再负责这款产品的研发，而是把主要精力转向如何让 Agent 在企业内部实现提效——这也是我今天分享后面两个重点。

今天我会着重讲 M3 有哪些能力，以及我们内部是怎么进行提效的。

图片引用: https://km.woa.com/asset/000100022607005ce0d5b8ceb04c7201?height=792&width=1407
先简单介绍一下 MiniMax。我们目前是一家全模态、所有模态的模型都在做的大模型公司。主要有两条模型线：一条是 M3 模型，这是今天会着重介绍的文本模型；除此之外，我们同时也在做多模态模型。比如视频生成，现在这个版本叫 Hailuo 2.3，是去年九月份左右上线的，下个月我们会更新 Hailuo 3 的新版本，效果应该能媲美今天的 Seedance。

此外我们还支持 TTS，这应该是国内调用量最大的文本转语音模型。大家今天听到的各种有声书，很多都是用我们的 Speech 模型生成的。我们还有 Music 模型，可以直接通过文本生成音乐。不过这些都不是今天介绍的重点。

图片引用: https://km.woa.com/asset/00010002260700f508738120d546c001?height=792&width=1407

重点还是 MiniMax M3。M3 是我们上个月 6 月 1 号、也就是刚好一个月以前发布的最新大语言模型。发布当天我们可以非常自豪地说，它应该是开源的 SOTA——因为当时 GLM 5.2 还没有发布。GLM 5.2 大概两周后才发布，表现效果确实不错，但它不支持多模态能力。所以到目前为止，在同时保持前沿 Coding、1M 上下文以及原生多模态的开源模型里，SOTA 应该仍然是 M3，这是加了很多前缀 buff 的说法。整体表现能力上，M3 已经接近 Opus 4.6。目前 M3 已经接入了腾讯的 CodeBuddy 和 WorkBuddy，如果大家日常使用的话，可以切换着来感受一下。

图片引用: https://km.woa.com/asset/00010002260700e532fa11b7e2473301?height=792&width=1407

我觉得 M3 目前跟其他所有模型相比，最大的优点还是参数量非常小，现在只有 400B 参数。这也是为什么我们在 Hugging Face 上每一次开源的下载量都非常高，很受开源社区欢迎。我觉得目前中美两国的开发者在 Hugging Face 上有一个很大的区别：国内开发者由于受制于卡的原因，很少有人自己去部署模型、起一个本地模型来跑 Agent；但在海外，独立开发者非常喜欢在自己的 Mac Studio 或单机上跑一个模型，他们更喜欢这种掌控权。而在整体 API 调用量上，M3 在 OpenRouter 上当时也是最高的。这里我们有一个视频。简单介绍一下 M3 的整体能力。

由于这次加入了多模态，M3 可以完成之前很多做不到的事情，比如 computer use，比如它对生成的网页有了更好的审美，还能基于网页进行 debug。这里是一个我们做 GPU 性能优化的例子，M3 可以长程工作 20 多个小时不停下来。这是一个 deep research 的例子，它可以生成一份上百页的技术报告，报告的图像也非常丰富。这里就让大家 overall 地感受一下 M3 的整体能力。

图片引用: https://km.woa.com/asset/0001000226070099dd341572ce485201?height=792&width=1407

不过今天是一个游戏会场，我就结合一下：如果大家把 M3 用到游戏开发里，可能会有哪些场景。由于我真的没有开发过游戏，所以只能凭我自己对游戏的理解，来看一下大家可能的一些需求。M3 这次应该是大幅加强了对3D的理解，以及基于Three.js 的3D理解，比如上下结构、整个空间布局。这里有两个X上的真实开发者做的例子：左边是他用一个prompt就生成了一个3D小屋，右边是他复刻的一个3D动画。我们来看一下这个例子。

前面我穿插了几个让M3去对比Opus 4.6的例子。右边大家可以看到是M3做的3D Three.js建模，这就是刚才说的那位X上的开发者——他通过M3复刻了一个电影里的视频片段，同时手还可以控制这个片段。还有一位开发者，基于M3做了一个完整的3D小屋模拟，小屋里有很多元素都可以交互。

这些例子就让大家简单感受一下。我相信今天很多游戏开发，可能之前是基于PRD开发，今天已经基于原型来开发了。对于一个不会设计的同事来说，他其实可以通过今天的AI大模型，很快地搓出像视频里这样的原型，这样就能大大加速游戏前期的研发流程。

除了这种偏Demo、偏原型的产品设计，M3这次应该也初步加强了在Unity、UE以及Godot这些比较专业领域的游戏开发能力，我们希望能够帮助更多专业开发者。这三个Demo也是一位X上的工程师做的，他基于已有的素材搓出了这种偏小游戏的场景。

图片引用: https://km.woa.com/asset/00010002260700cbecfcf6ec54499701?height=792&width=1407

除了让大模型加入游戏开发的过程，我相信现在很多游戏也在尝试如何把AI真正纳入游戏内部。比如现在有很多探索，让NPC参与游戏动画、扮演游戏角色，再让一个自主的Agent变成一个队友；再比如开放世界里可能会进行一些生活的模拟。这方面非常考验大模型的Roleplay能力。

MiniMax应该从2022年就开始尝试做角色扮演——当时模型还干不了像今天这样严肃的工程研发，所以我们只能先选择角色扮演和情感陪伴这样的路线。当时Talkie和星野这两个产品，除了已被战略放弃的 Character AI之外，应该是全球最大的角色扮演社区。基于角色扮演，我们做了非常深入的研究，在M2阶段还单独为角色扮演发布了一个模型，叫M2 Her。

右边这两张图可以看出，我们在M2的研究过程中，主要想让模型相比非角色扮演类的模型提升三个能力：
第一个是世界一致性：现在很多时候你用大模型做角色扮演，聊一段时间之后它可能就忘记自己所处的世界和真实世界的区别了。比如你让它扮演李白，问李白冰箱是什么，如果没有很强的世界一致性，它就会一本正经地给你解释什么是冰箱，那就完全跳出角色了——一个古人理论上不应该理解冰箱这种未来产品。

第二个能力和长程稳定性有关：我们发现在Talkie和星野里，用户跟AI的聊天轮次往往很长，一百轮其实只是起步，很多用户会持续跟一个 AI 聊十天半个月，进行上千轮甚至上万轮对话。如何让一个角色在上万轮之后剧情还能持续推进，这是之前一个非常难的问题。很多时候你在system prompt里告诉它这个角色应该推进 a、b、c、d 剧情，但玩家聊着聊着往往会忘记主线剧情，陷入死循环，越聊越没意思。游戏里其实也类似，想让NPC持续推进剧情，同样需要非常强的长程稳定性。下面那张图就证明了M2 Her在长程稳定性上远远超过同期所有其他模型。

第三个能力是感知偏好：模型需要懂用户的潜台词，不要把用户的所有事情都直白说出来。这些可能就是我们在Roleplay上深厚的积淀。这次我们把Roleplay的训练语料加入了M3的训练过程，结果发现——在办公场景里，也就是大家跟AI聊天的过程中，AI会变得更有情感。这也是M3的一个意外发现。

接下来跳出M3这种模型的介绍，主要讲一下过去一年里，MiniMax内部是怎么对个体提效、以及对组织进行提效的。

图片引用: https://km.woa.com/asset/00010002260700193e8c67944f459601?height=792&width=1407

上面这套步骤是我们总结出来的，讲的是如何让AI深入参与到日常工作流、让AI Agent参与进来帮我们提效。我先说一个暴论：在有AI Agent的时代，我们所有人其实都应该把自己当成一个管理者，因为你管理了一个基层员工，而这个员工就是一个AI Agent。这里的Agent包括今天你能用到的Hermes、OpenClaw，甚至WorkBuddy、CodeBuddy，都属于AI Agent。

那如何做好一个管理者呢？我特别喜欢《卓有成效的管理者》这本书，它在前三章提到一个非常重要的观点：时间是管理者唯一不可再生的资源，管理者首先要管理的就是时间。对我们来说，需要去思考在日常工作中哪些步骤比较冗余、哪些步骤占用了大量时间，能不能把这些工作平行地交给AI Agent，让它把你这部分重复的工作取代掉。这件事在内部推进，也主要是我在做。大概去年这个时候，我找到公司所有职能线做深入访谈，比如 HR——我跟HR聊，让他们把一天的时间安排写出来，然后发现大量占用HR时间的其实是每天上网找简历。于是我们开始推进一个HR Agent，让它帮HR自动找简历，整体提效。总结一下，第一步就是先发现整体工作的冗余，接下来就是设计方案了。

图片引用: https://km.woa.com/asset/00010002260700ae5d45eb6e164ce401?height=792&width=1407

我们需要设计一个自动化方案，把人的时间释放出来。这个方案该怎么设计呢？

首先得确定这项任务到底是不是一个能被AI Agent取代的任务。怎么评判？有一个非常简单的标准：这份工作交给AI Agent，它的输出是不是可以验收的、有没有验收标准。比如你让AI Agent 去寻找 100 份某种简历，这是一个清晰、可以用一句话描述的标准；但你让Agent 去生产 100 个小游戏，方向太多、太 diverse了，没有办法验收。

接下来是给这个Agent搭配所需的所有工具，包括但不限于MCP和CLI，需要打通企业内部或你依赖的一些数据源，把数据源交给AI，让AI帮你理解这些数据。待会我会简单介绍，我们内部其实是大力推进CLI的，把之前企业办公的所有工具全部CLI化做了一遍，也会讲为什么我们选择了CLI。

第三点是给AI交代一个完整的上下文——你把它当成一个新员工、一个刚入职的实习生，告诉它业务背景是什么、需要达成什么样的目标、以及不能触碰的产品红线。人在这个过程中其实是为AI Agent兜底：它可能遇到一些没见过的场景，人就去做非标准化场景的兜底。

最后一步是拆解：很多人一上来觉得自己都理解不了，也不帮AI拆解就直接让它做，那整体效果很难保证。我们的建议是，让AI Agent加入工作流时必须一步一步拆解，先尝试从A到B、B到C，如果整个链路能跑通，再把B这个中间节点坍塌掉，直接从A到C，这样整体效果会比较稳定。

图片引用: https://km.woa.com/asset/0001000226070057c4eb841ba140bf01?height=792&width=1407

这里简单介绍一下，为什么我们内部把100多个不同的平台——比如数据平台、外部信息源、调研报告、研究数据源——都通过CLI去包装，而没有用MCP。

MCP应该是两年前提出的一个协议，本质上它把一个工具的所有参数、所有信息都暴露给调用的大模型，好处是能让大模型清晰地把工具调用起来，但缺点是占用了非常大的上下文。我们简单尝试了一下：如果把87个工具通过5个MCP封装暴露给大模型，光这部分工具参数可能就已经占用了非常大的上下文。而如果通过CLI让它运行在bash命令里，就几乎不占上下文——你只需要告诉它一句话，说这个CLI可以使用、你自己去探索一下就行，这是一种对上下文友好的方式，这是我们选CLI而不选MCP的第一个优点。

第二个优点是CLI在bash下天然支持串行：大模型生成一次工具调用，里面就可以包含很长的一串「先依赖A、再执行B、再执行C」，只需要调用一次大模型就能串行执行多个工具；而MCP并不支持，它必须先执行完A，把结果反馈给大模型生成B，再把B的结果反馈给大模型生成C，这个过程非常绕。还有一点是CLI比MCP更友好的地方——它支持热插拔。热插拔的意思是在对话过程中可以随时给它增加工具。

不知道大家有没有这种体验：跟一个Agent对话了很久，突然发现缺少一个工具，如果这个工具要通过MCP的形式接入，整个session就崩掉了，因为你需要重启session，之前的对话历史就没有了；而用CLI就很简单，你告诉它去哪里使用这个CLI，如果没安装，一句话就能让它去安装，整个对话过程中都可以持续运行。这是CLI 非常大的优点，也是我们内部为什么持续推进CLI、而没有用MCP去封装的原因。

图片引用: https://km.woa.com/asset/000100022607002e2682e5d6ad400701?height=792&width=1407
回到今天的主线。当我们用 AI 尝试一步完成某个任务的自动化流程之后，接下来就是如何把整个流程固化，这也是今天大家可能经常刷到的一个词——Loop Engineering。这是最近一两个月突然爆火的词，是Claude Code的产品负责人在两个月前的一次会议上提到的。但我觉得这个词有点过誉了，因为loop这个功能本身其实很早就有了。今年春节爆火的Open Claw，也就是我们常说的「小龙虾」，我发现很多人用它的第一个场景，就是让它定时每天给自己发一封日报、总结一下有什么新闻，这就是一个很典型的Loop 场景，也就是今天常说的Loop Engineer。

当我们想固化流程的时候，我觉得第一步是找到一个性能足够的模型就好——因为任务流程比较固化时，你没必要用最贵的模型（如果token无限的话可以忽略这一点）。第二步是设置自动化的触发机制，定时任务这个能力应该是所有Agent产品的标配了，但loop本身目前可能只有Talkie或少数产品支持。loop和定时任务区别也不大：定时任务是每天或每小时，loop可能是每隔几分钟执行一下，本质上都是希望通过自动化地发送prompt来减少human-in-the-loop的过程，减少人类发prompt的时机，让人类不要成为整个 Agent工程的瓶颈。第三步是把第二步里跑通一次的整体流程Skill化，或者通过一些system prompt的定制、以及工具沙箱的组合让它更标准化，形成一个可复用的线上环境工具包。这里我们更推荐选择云端环境，因为本地环境往往可能由于自己不小心就搞崩了，而一个稳定的云端环境可复用性更强。用云端版本还有一个优点，就是整个运行轨迹是可记录的状态，之后可以帮助大家持续优化。

图片引用: https://km.woa.com/asset/0001000226070031b4b99558b445aa01?height=792&width=1407

在通过 AI 提效这方面，我一直在持续推进一件事，就是让大家在使用AI Agent的过程中，一定要在群聊里使用，而不要单聊使用。在群聊里使用有非常多的好处。第一个好处是，你把自己的操作轨迹暴露给其他人，让别人可以学到，这对组织内部有很大的价值——其他人就不需要被专门培训了，他通过看你如何跟 AI 对话，就知道你开发了整个流程，也知道自己什么时候可以复用。第二点是，别人也可以持续帮你迭代整个流程。我们内部现在有一个平台，叫「实习生」，等一下会给大家看。这个平台相当于集成了不同业务线的所有Skill，而这些Skill是开放给大家持续迭代的。当你自己维护一些Skill的时候，可能还没那么容易，但多人一起共建就变成了一件容易的事。所以我们内部现在在群里使用大模型时，token是不计费的；如果你在本地使用大模型，我们才会给每个人一个额度。

图片引用: https://km.woa.com/asset/000100022607001cf448bd4551444c01?height=792&width=1407

这里是我们内部的一些场景。这个产品我们叫它Agent实习生，在去年Q3就已经上线了，里面集成了非常多职能部门同学在用的场景。这里图比较小，它打通了几乎所有我们可能用到的工具，把它们封装起来，给内部提效。

图片引用: https://km.woa.com/asset/000100022607000a98c543c4894d2101?height=792&width=1407

这里给大家展示一个我自己的具体例子。我们做大模型，本质上是暴露API给用户。从去年开始，AI Agent在开源领域非常火，我们发现平均每新增两个开源项目，就有一个是跟大模型有关的项目。这对我们这些维护API的管理方来说，是一个非常大的挑战：每次发布新模型之后，用户都会问「这个框架为什么还没有支持」「你们这个新feature为什么还没上线」。目前我们需要持续维护两三千个不同的开源框架，用户希望在我们API上线的第一天，就能把新模型ID和新功能feature支持起来，这是一个非常大的挑战。刚开始我是人肉地一个一个框架去上手适配，每次发新模型都要花三四天时间做这件事，后来发现框架实在太多了。

图片引用: https://km.woa.com/asset/000100022607004de85f155271499401?height=792&width=1407

我的解决方案就是设计了一整套Agent Loop方案，交给了一个账号。这个账号有点像真人，叫Orpheus，如果大家用GitHub，现在还能搜到它。这个账号从今年3月份上线，到现在三个月，已经提交了2700多个commit，成功合入了1000多个不同的项目。

这套方案我大概花了一周时间打磨，放在我们的平台上。目前我只需要每天跟它沟通一次，它每天会在右边发一份过去一天的日报——今天新发现了什么有价值的仓库、成功解决了什么问题、以及接下来它可能需要什么帮助。我基本上每天花三五分钟跟它对话一次，帮它把上面的问题解决掉，然后它就可以持续地工作。

图片引用: https://km.woa.com/asset/000100022607001647ed1260ba43f901?height=792&width=1407

这套东西我是怎么设计的呢？简单来说，就是通过刚才提到的「实习生」产品，有一个内部定时触发的机制。它唯一需要用到的工具其实就是一个GitHub的权限，我把这个密钥告诉它，通过每天的定时任务去触发。在触发的过程中，由于希望它能提高效率——它需要持续维护上千个仓库，如果只靠一个主Agent持续运行会非常低效——所以我们设计了一套并发机制：主Agent只干活不写代码，它去理解两三千个仓库目前有多少个任务，安排一个任务队列，再把任务交给子Agent，每个子Agent完成队列里的一项任务。比如需要去仓库A修复某个 bug，主 gent负责分配任务，子Agent负责并行执行。这个方案设计得挺好的，但上线当天就消耗了两三千美金的Token，最后老板都找到我了，不知道我为什么这么疯狂地烧Token——因为当时用的是海外的模型。现在这个项目已经完全交给MiniMax M3来做，一天的成本基本上只有一百多块钱。

图片引用: https://km.woa.com/asset/00010002260700e75952fc62c94c0c01?height=792&width=1407

以上就是关于我们如何让AI Agent加入日常办公、作为个人提效手段的介绍。但我也发现一个问题：我们让每个人的效率都提高起来，可对整个公司来说，效率并没有增长多少。

图片引用: https://km.woa.com/asset/00010002260700431789bbf700413b01?height=792&width=1407

这里有一个很经典的例子——100年前，福特公司是全球最早通过流水线生产汽车的公司。在福特真正build出流水线之前，工具也都是发放给每个车间员工的，员工领到了最先进的工具，但整体效率并不高。这就有点像我们发现的问题：我们给每个员工都发了 Token、发了大模型、发了AI Agent，但整个组织的效率好像并没有变高。福特是在1913年发明了整套流水线，让汽车在流水线上跑，每个人只需要解决流水线上一个环节，整体效率就提高起来了。所以我们内部也在反思：是不是目前的组织架构并不特别适合我们现在的研发流程？因为AI的 coding效率提高了，但研发流程的架构并没有变高效。所以我们从去年开始思考这个问题。

图片引用: https://km.woa.com/asset/00010002260700a36b0194bb8e4ad901?height=792&width=1407

我们首先复盘了一下：其实公司整体的研发线，跟过去一二十年所有互联网公司的研发职能是一样的——产品先写一个PRD，我们基于PRD去驱动，一步一步走到设计、前端、服务端、测试、发布。我觉得这也应该是目前大部分互联网公司或软件公司的流程。这个过程非常依赖人与人之间的配合。举一个很简单的例子：产品可能发现有一个文档的配置写错了，但产品没有这个仓库的权限，或者也不知道这个配置该怎么改，就需要去找人，比如找个前端。前端说「我在忙，等你排期」，可能排到几个小时之后，前端才有时间看你这个问题。

图片引用: https://km.woa.com/asset/00010002260700702ef575b6d0495b01?height=792&width=1407

所以我们在去年Q3干了一件相对比较大胆的事：把公司所有仓库的所有权限直接开放给所有人，包括产品经理和HR，不再做任何权限管理。因为我们觉得，仅仅是代码层面的权限管理，价值已经没那么大了，整体的提效才是对整个公司价值最大的，所以不希望在权限上做任何block。

这件事之后，我发现一个很有意思的现象：很多相对简单的事情，其实从有idea的那个人——而有idea的人不见得是产品经理，也可能是个研发、甚至跟这条业务线没有任何关系，但他就是有一个想法的人——就可以直接去帮你解决一个技术问题。所以我们去年从PRD驱动转型成了基于原型的驱动，甚至产品经理想改的时候，也是先把原型画出来，再跟我们真正的研发一起推进上线，这也是去年的一个变化。

但这种事情到去年年底又发现了一个问题：产品写代码写得实在太快了，以至于没有人敢上线。我们之前有个很有意思的现象：过年期间，一位新入职的产品经理特别有passion、特别有动力，他觉得我们那个技术方案写得不好，一个人过年在家写了8万行代码提交上去，但没有人敢保证这8万行代码能真正稳定上线。

图片引用: https://km.woa.com/asset/00010002260700eaa6da591b43417501?height=792&width=1407
所以到今年Q1，我们整体的研发线也在思考：怎么样才能解决这样的问题？怎么样的组织架构，能在coding已经非常快地涌现的情况下适配得上？所以今年Q1，我们所有的研发线其实已经没有传统意义上的后端、测试、服务端、前端这种概念了，全部转化成全栈。我相信这在一些小公司里推进还是比较顺利的。

合并成全栈之后，整体的研发流程可能就分为三部分：第一部分是有idea的人决定我们要做什么；第二部分是决定做的时候，我们怎么去实现；第三部分是实现完之后，能不能安全地把它推上线。

图片引用: https://km.woa.com/asset/00010002260700caee36c4f3dc4a1d01?height=792&width=1407

目前我们的组织架构变成了这个样子。上面是我们过去比较传统的组织架构：客户端分为客户端A、B、C、D不同的小组，各自完成不同的feature，再跟服务端的A、B、C、D几个小组配合，可能还有一个单独的测试部门。而现在，我们相当于把整个团队打散重组，基于feature或者基于方向来划分，确保每一个方向都有一个不同技术栈的专家，每一个技术仓库都有一个owner去守护——就是下面画的这个架构师。架构师需要确保最后merge的每一行代码都是稳定可靠的。

在这个过程中我们发现，架构师的价值越来越大，因为他需要去验证什么是对的：可能方案A也能跑、方案B也能跑，但适配你们公司架构、适配你业务场景的，可能只有一个唯一的答案，所以「判断什么是对的」这件事变得越来越难。还有一点是「提出一个方向」——什么是好的方向，也变得越来越稀缺了。以前一个产品经理提出一个idea，到真正落实、推进，可能是以周为单位的事情；如果研发效率大大提升了，那提出idea、决定产品方向该往哪走，就又变成一个瓶颈了。我每天都能完成你过去一周才能完成的新feature，那你什么时候才能提出足够多、或者足够对的方向呢？这其实是比较难的。

图片引用: https://km.woa.com/asset/000100022607001fadc0febb57435501?height=792&width=1407

这是Google I/O上个月提出的新型人才架构，我觉得也是目前我们公司比较认同的架构——我们需要一个“T 型人才”。什么是“T型人才”呢？“T”横的这一行，是指你首先要把AI用得非常深刻，在所有领域都要把AI用起来；而“T”那一竖，是指你得有自己一个很长的长板，在某个领域深耕，这就是刚才提到的架构师领域。

所以我们今天招人也很在意：你在某一个领域，是不是真正理解得比今天的大模型还要深刻？这是目前比较难的一个点。除了在某一个领域深耕，我们也希望你能同时加强左侧——相邻的工程领域。比如你之前对后端整体架构非常熟悉、对高性能了解很深，那你能不能同时通过AI去实现一个前端或客户端等相邻工程领域的工作？还有就是，对工程师来说，我们也希望能加强对非工程领域的理解，比如用户调研或数据分析——现在通过你自己加上一个Agent，是不是就能完成之前产品经理做的一些决策？我觉得这个“T型人才”应该是目前所有工程师都需要思考的问题：自己怎么加上AI，去对整体业务目标产生更大的贡献。

图片引用: https://km.woa.com/asset/0001000226070043cb18bb93be421301?height=792&width=1407

最后我简单总结一下今天这套面向组织提效的方法论。我们判断，AI真正进入我们的工作领域可能也就一年时间，我们仍然处在类似福特自动化流水线非常早期的阶段。我们相信，AI完整地演进我们整个组织变革的进程，可能是一个以十年为周期的单位。所以我觉得目前大家需要对AI对组织的演进有足够的耐心，但不要躺平，不要等着说要演进出一个非常完美的方案——要保持持续的耐心、持续地思考：AI目前对我们组织的哪些问题是可以持续提效的，提完效之后组织的瓶颈又在哪里。第二步是要理解，把组织当成一个产品去思考、去打磨，这样才可能继续进行一些深层次的重构。

最后一点，也是今天想跟大家分享的：现在coding、或者说研发这件事可能变得越来越简单了，但整体的判断反而变得越来越稀缺。如何在AI时代提升自己的判断，这件事变得越来越有价值，我觉得这也是目前每个人都需要思考的问题。
