# 课题原则（rules/PRINCIPLES.md）

> 所有 spec / task / harness 决策必须符合以下原则；冲突时以本文档为准并记录 decision。

## P1. 引擎无关、资产中立
- P1 只产出标准资产：立绘（PNG 分层，可进 Live2D/Spine）、语音 WAV+字幕、3D glTF/GLB、人设 JSON
- 引擎层只做"导入 + 运行时"，不做生成
- Agent 与引擎解耦：引擎通过 HTTP/WS/MCP 调用 Agent 服务，换引擎不换 Agent

## P2. 每层产物可见（工作台形态）
- 管线 = Job 队列 + 阶段状态机，每阶段产物可预览/下载/单步重试
- 失败不整条重跑，定位到阶段（这也是后续跨层归因的产品基础）

## P3. 复用优于自研
- 每个 part 必须先列「开源/论文/产品借鉴清单」（见各 spec），能借的借，只自研衔接与编排
- 禁止"重新造轮子"式开发（例：不用自己写 TTS、不用自己写生图 base model）

## P4. 一个 part 一个 part 来；评测后置
- 不并行铺开多个 part；做透一个再进下一个（依赖允许的并行需在 ROADMAP 标注）
- P5 评测在 P1-P4 跑通前**不实现**，只保留目标占位

## P5. 接入现有游戏是正式路径之一
- 不是只能从 0 建游戏；Mod/注入（白名单安全动作 + 回归检查）是同等优先级路径

## P6. 契约先行
- 人设卡 JSON Schema、资产包规范、Agent 协议、白名单动作定义，都是先定契约再写代码
- 契约变更必须更新 spec 并记录 decision

## P7. 本地优先、资源可量化
- 默认本地可跑（离线模型/本地推理），云能力作为可选开关
- 每个生成任务记录耗时/显存/成本，喂给后续评测矩阵

## P8. 真实工程不流于表面
- 每个 task 有可验证的产出与验收标准；demo 要能跑、能看、能量化
- 反对"表面功夫"：验收不通过就是未完成，宁可不写代码也不写假进度

## P9. 工业主流优先（防"为了省事选非主流"）
- 技术选型以 `spec/TECH-STACK.md` 为唯一依据：首选工业主流（商业产品 / 大厂开源 / shipped games 验证的开源）
- 社区项目只作研究参考，不默认进主线；如必须使用，需标注理由 + 主流替代
- MVP 可以"落在主流方案的一个子集上"，但**不能选一条非主流的旁路**
- 选型改动必须更新 TECH-STACK.md 并记录 decision
